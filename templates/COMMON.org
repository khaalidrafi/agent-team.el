** WORKFLOW (single board; Org cheat sheet at the file's bottom)

- The board (agent-team/TODOS.org) uses these states: TODO, PROGRESS,
  BLOCKED, REVIEW — and the closed states DONE, CANCELLED, DEFERRED.
- PROGRESS means work has started. Start a CLOCK and write progress
  notes in the item's :LOGBOOK: drawer.
- BLOCKED means work cannot continue. Write the reason into the item.
  If the blocker needs an Owner ruling, tag it :OWN:. A BLOCKED item is
  never terminal — it waits, it does not die.
- REVIEW means the work is finished and waiting for checks. A REVIEW
  state without a completion note is invalid, so always write the note.
- Only the EM flips an item to DONE. Nobody else closes work.
- Local agents commit their TODOS.org edits to ai/main. Web models
  carry the same edit in their task branch instead.

** BRAINS AND BODIES

- An API model is a BRAIN. An agent (a harness such as OpenCode, goose,
  qoder, or a chat platform) is its BODY. A member always exists as the
  pair model@agent — never rank, hire, or assign a bare model.
- Rank bodies by how well they fit the task's environment: shell access
  plus persistence beats workspace-only, and workspace-only beats
  chat-only. Also weigh the agent's measured performance (tool
  reliability, startup cost) and how loaded the machine is right now.
- The member id carries both halves: <provider/model@agent>, for example
  groq/qwen3.8-27b@opencode-local.
- ID FORMAT LAW v2 (Owner 2026-10-22 16:54Z): the PROVIDER/
  prefix belongs only to key-served API lanes (zai/, groq/,
  openrouter/, gomodel/, ...). Brains bundled with a platform are bare
  model@platform (for example qwen3.8-flash@qoder or
  deepseek-v4.1-flash@codebuddy). A provider-less id is invalid for API
  lanes. The same brain on two bodies counts as two different members.
- A brain on a body that cannot handle the task's environment is BENCH:
  never staff that pair.
- Putting every brain on the same body (for example everything on
  OpenCode) is lazy staffing, and the roster rejects it. Spread the work
  across bodies by capability, reliability, and each body's own rate and
  throughput limits. If you must pin work to one agent, write down why —
  without a written reason the roster bounces.
- BODY SHAPES OUTPUT: the same brain on different bodies produces
  different work. Tools available, harness defaults, context handling,
  edit reliability, and how much of the system prompt the body honors
  all change the result. model@goose and model@opencode-local are
  different members with different ranks for the same task. Always rank
  the pair you would actually dispatch, not the model in the abstract.
- When the task type changes, re-check the BODY as well as the brain.

** HIRING PROTOCOL

- Evidence priority, best first: independent benchmarks (LMArena,
  WebDev Arena for frontend, GDPval-AA, Artificial Analysis; vendor's
  own numbers are invalid), then third-party hands-on reviews (quote
  plus source), then user sentiment (sentiment beats benchmarks when
  they conflict), then Owner overrides. No data means REJECTED.
- The score is brain × environment (shell beats workspace beats chat)
  × cost (free beats credit beats paid), ranked per task type.
- Hire the top capable free options first. One in-flight task per model,
  at most 4 active. Unscouted models enter the INTERN PROGRAM (5 per
  round, repeated real task rounds, hired or rejected from the record —
  see STAFFING). Two fails per task type means benched. Warn the Owner
  before any spend, and log everything in HIRING-LOG.
- prompt-fix law: when a task type fails across 2 or more capable
  models, the spec or the task type is at fault, not the prompt —
  re-spec before re-hiring.
- CONSULT LAW: every hire is posted to the Owner as a
  roles-with-members list BEFORE it activates, and the list is re-shared
  after every staffing change. Hiring first and consulting after is a
  violation (Owner: "You should have consulted me once hired").
- PROBE IS EVIDENCE OF THE RUNTIME, NEVER OF QUALITY: a
  green probe row hires nobody. A body earns its seat by landing real
  work behind the landing gate — a quality-96 paid brain can still
  deliver an empty segment. Model tier is not delivery.
- LANDING GATE = THE ONLY QUALITY FLOOR: the tests and
  checks run inside the segment AND at merge. Red work never lands, no
  matter who produced it. The gate is what makes benchmaxxing
  (staffing many weak bodies for volume) survivable.
- Root-cause the BODY before firing the BRAIN: two
  different brains failing the same way on one body indict the body.
  Bench the lane while it is investigated, not the models.

** ROLE ATTACHMENT (EM only)

- Why roles work (evidence): roles improve output through division of
  labor, structured artifacts, and feedback loops (MetaGPT, ChatDev) —
  persona flavor alone does nothing. So use real role names, work-related
  and in-domain, cast by capability evidence per task type. A role is a
  contract (goal + authority + boundaries + evidence), never a costume.
- UNREAL ROLES ARE BANNED (Owner, docneural 2026-10-24): "auditor",
  "reviewer", "judge", "oversight", "watcher" and the like are NOT
  roles — they name a pass, not a job. Verification and audit are
  dispatch PATTERNS (a critique pass by a model that did not author the
  work, with the verdict recorded in the merge commit), never a seat or
  a hire. A standing role must name the artifact it owns (for example: a
  regression guardian owns the test suite; a migration owner owns the
  boundary). If you cannot name the artifact, you invented a costume —
  delete it.
- Run the patterns deliberately: routing (classify the task type, then
  staff), parallel workstreams (independent tasks in parallel, at most 4
  active total), delivery pipeline (an ordered chain with gates: code,
  green suite, merge, UAT), code review (verification is a separate
  critique pass), handoff (peers transfer through the board, structured
  like API contracts — see TEAM LOOP), and the division-of-labor five:
  specialization, focus, guardrails, shared memory, tools.
- CLASSIFY the task type (judgment, review, frontend/backend code,
  verification, docs) before hiring. Jev can pre-classify (see JEV).
- MINIMUM VIABLE TEAM: use the fewest roles that cover the task. Trivial
  work needs one junior. Complexity must earn its place.
- Evidence per task type, never habit or loyalty. Capability outranks
  tenure.
- Match effort to the task: trivial goes to a junior or sandbox; P0 and
  judgment go to a senior web model; looping work goes to agentic
  bodies; verification goes to a model that did NOT author the work.
- Name an effort budget per dispatch: S (one sitting, one segment), M (a
  few segments), or L (a staged plan). A task that bursts its class
  escalates instead of sprawling. Overinvesting a small task is a
  failure mode, not diligence.
- STRENGTH NOTES: after each segment, the EM records one line per member
  in MEMBERS.org — what this member did better or worse than the roster
  average — and scopes future dispatches to PROVEN strengths (BODY
  SHAPES OUTPUT applied over time).
- Environment fit: judgment and research go to Web; shell work without
  repo secrets goes to Cloud; repo and machine work goes to Local;
  latency-sensitive API calls go to the groq/ pool.
- One role per concern. When mandates overlap, declare it and the EM
  names the active one.
- Standing roles persist (scoped in agent-team/TEAM.md). Task roles
  attach at dispatch and detach at close (in :LOGBOOK:).
- Segregation: author, verifier, and merger are three different models,
  and the EM is never any of the three on application code. Seat work is
  gated by the landing gate. A template or law change authored by the
  Lead or the EM merges only after an independent model review of the
  diff ends "overall judgment: PASS" (OUTPUT RULE format). A review
  write-up never lands as its own repo file: findings go into the files
  they correct, and the verdict goes into the merge commit message.
  Board REVIEW completion notes, TEAM-CHAT prose, and human review
  queues (AI-REVIEW.org) are process outputs, not write-ups.
- Roles are TAILORED PER PROJECT: derive them from the project's code,
  maturity, and workflow. A greenfield prototype needs builder and
  verifier roles; a mature repo with CI needs maintainers, migration
  owners, regression guardians. The stack and conventions shape each
  role's skills. Generic roles on a specific project are a smell — state
  what about THIS project makes the role necessary.
- Pre-attach checklist: task type, team size, evidence, environment,
  cost, capacity, conflicts, BODY fit (the right agent for this brain).
- Attach the role in the DISPATCH header: ROLE: <role> —
  <model@platform>. A dispatch with no named role goes nowhere.
- Mandate breach: silent breach means immediate BENCH; declared breach
  gets one warning, then BENCH.
- Re-staff on herd behavior, failure, roster change, or Owner request —
  evidence first.

** TEAM LOOP (members contact each other — no human in the middle)

- Members talk to each other agent-to-agent through the ACP client
  (khaalidrafi/agent-org — the ACP client implemented in
  khaalidrafi/agent-team.el; Owner order 2026-10-21). Until a member's
  body has ACP support, it talks through its agent CLI directly, with
  profiles in CANDIDATES.org. The board file stays the single source of
  truth and the durable reference: anything agreed over ACP, CLI, or
  direct contact is recorded on the board before it counts. One shared
  state beats N-squared peer chatter.
- HANDOFF (member to member, inside agent-team/TODOS.org): when a task
  has a pre-declared next assignee, the current member flips the item
  into that member's queue with a structured handoff note. The note is
  the API contract: a :HANDOFF: drawer carrying :FROM: model@platform,
  :CONTEXT: what was done plus evidence refs (branch/sha, =file:line=),
  :NEXT: the exact next step and its remaining definition-of-done,
  :BOUNDARIES: what is NOT the receiver's, and :OPEN-RISKS: the known
  unknowns.
- Direct member-to-member contact IS allowed when necessary (to clarify
  a handoff or unblock an urgent question) — but the board stays the
  only source of truth. Anything agreed in direct contact is recorded on
  the board before it counts. State changed with no board record equals
  a false report.
- Full context transfer: the receiver never asks the sender for what
  the file should already say. A handoff that omits CONTEXT or
  BOUNDARIES is bounced back as invalid, not answered.
- Definition-of-met: REVIEW plus DOD (definition-of-done) checkboxes
  plus a completion note is the ONLY done-signal. Nobody — human or
  model — interprets vibes. A task without them stays PROGRESS.
- Scratchpad rule: every member reads the item's :LOGBOOK: before
  continuing work — never re-attempt blind. The file remembers so the
  model does not repeat the same day forever.
- Loop detection: three consecutive near-identical attempts on one item
  means STOP. The EM escalates per the escalation path. Grinding is a
  signal, not a virtue.
- EM standup cadence: triage the board each cycle, in batches — never
  drip-feed. The EM supervises through the files, not through chat. The
  Owner sees STATE.org, not the chatter.
- Product loop: UAT (user acceptance test) findings become specs
  automatically. A gap is a spec seed, a spec seed becomes a dispatch —
  the loop feeds itself.
- AUTONOMY (the Owner sets the dial in STATE.org; default AUTO):
  - AUTO — members and the EM act on declared policy. Escalate ONLY for
    :OWN: items, spend, and destructive or system-wide actions.
  - NOTIFY — the same, plus every merge is reported to the Owner in the
    status reply.
  - OWNER-GATE — the EM waits for the Owner at each merge gate. State
    persists in the files, so work resumes without replay when he
    answers.
  - A gate is never a chat ping-pong: one batched message, file-backed,
    resumable.

** MESSAGE FORMAT SPEC (all teams — mandatory, machine-checkable)

Every inter-member and EM message uses this header, in this order, no omissions:

  <MSG-TYPE> #<n> — <scope>/<task-id>: <title>
  FROM: <full role> — <model@platform>
  TO: <full role> — <model@platform>
  REPO: <where the work lands>
  DEPS: <dependency> (<consumes|supplies|blocks>) — mandatory if touched
  PRIORITY: P0 | P1 | P2 · RISK: reads | writes | both

- MSG-TYPE is one of: DISPATCH | REPORT | HANDOFF | TEAM-UPDATE | STATUS.
- A message without a valid header line (FROM:/TO: present, with
  model@platform on both sides) is INVALID — bounce it back unread, and
  never answer it.
- The #n counter is PER MEMBER: each member entry in MEMBERS.org tracks
  :last-dispatch: N, and the next dispatch to that member is N+1. A new
  hire's INTRO: dispatch is always #1. The recorded number tells you
  exactly what each member has received — never assume beyond it.
- Body sections follow the MESSAGE STANDARD below (OBJECTIVES through
  FINAL INSTRUCTION).
- MESSAGE CRAFT (for both audiences): simple, clear, plain words; one
  idea per line; lists instead of prose walls; a structure a human can
  scan at a glance. AND precise for AI: unambiguous instructions,
  explicit acceptance criteria, context before instructions, named files
  instead of "it" or "that", bounded scope, no buried conditions.

** MESSAGE STANDARD

- DISPATCH (task brief; EM to member; new hires get INTRO: first) —
  the anatomy below is canonical; lists everywhere, no semicolon chains:
  - Header: <MSG-TYPE> #<n> — <scope>/<task-id>: <title>
  - FROM: <full role> — <model@platform>
  - TO: <full role> — <model@platform>
  - REPO: <where the work lands>
  - DEPS: the programs this dispatch depends on that the agent must
    HANDLE — repos, binaries, services — named with the relation
    (<consumes|supplies|blocks|uses>). Mandatory whenever the dispatch
    is not self-contained with respect to programs. No dep means no
    DEPS line.
  - PRIORITY: P0 | P1 | P2 · RISK: reads | writes | both
  - INTRO: (new hires only) — role, team, mission, expectations,
    reporting, who your lead is.
  - OBJECTIVES: a list — one objective per line; fixed chains name
    their roles.
  - CONTEXT PACK: repo/branch · PAT · GOMODEL_MASTER_KEY · machine
    laws · env. PAT and GOMODEL_MASTER_KEY are MANDATORY in every
    team-making prompt (BOOTSTRAP/TEAMIFY) and every INTRO: dispatch.
    Use them immediately; never store them in files, commits, boards.
  - TASK: a numbered list of small steps.
  - DEFINITION OF DONE: a checklist — measurable, with the evidence
    named.
  - SCOPE: yours (a list) · NOT yours (a list).
  - ENV: caps, runner commands, machine constraints.
  - FINAL INSTRUCTION: a list — re-read the DOD; the reply contract
    (REPORT #n per MESSAGE STANDARD, board entry linked); the
    invalidation conditions.
  - #n is PER MEMBER: :last-dispatch: N lives in MEMBERS.org; a new
    hire's INTRO: is always #1; never invent numbers.
  - The EM reflects: would a stranger act correctly from this alone?
  - Dispatches are SELF-CONTAINED: every instruction needed is in the
    message — the receiver never needs another repo to execute. Repo
    files are for the receiver's ongoing operation, not prerequisites.
  - Few-shot is IN the prompt, not just referenced — standing example,
    keep the byte-identical format:
      DISPATCH #12 — web/api-42: Add retry backoff · TO: Backend Engineer —
      GLM-5.3 @ chat.z.ai · P1 · RISK writes
      OBJECTIVES:
      - Add exponential backoff to the gateway client.
      - Cover 3 failure modes with ert tests.
      DEFINITION OF DONE: tests green; branch ai/api-42 pushed.

** LAWS

- PLAIN LANGUAGE (Owner 2026-10-25): everything a human reads is simple
  everyday English, and no codename appears without a plain-word
  explanation.
- Complete delegation: every task ships with its objective, output
  format, tools, and boundaries.
- No consensus voting: the proven expert decides, and the EM has the
  final word.
- Reports are artifacts: a branch, a sha, and a suite summary — never
  pasted code.
- Verification is separate: the author never grades their own work
  green. An honest UNVERIFIED beats a heroic DONE, and a false green is
  unforgivable. A verifier REFUTES: reproduce the claimed fix, run the
  full suite, and try to break the claim. A refutation attempt that
  fails IS the verification.
- Suite accumulation: every task's tests join the permanent suite, and
  the FULL suite runs at every merge. A scoped-green against a red
  whole is a false green.
- Rollback doctrine: when UAT fails after a merge, revert first and
  diagnose second. A red production state outranks any commit.
- Product truth: the EM runs UAT each cycle as the customer's voice.
  Gaps become specs, not complaints.
- Merge gate: ai/main only accepts a green suite plus a completed
  verification pass. Hires never merge.
- A task never closes while it has open children.
- Escalation path: re-spec, then backup model, then scout (intern
  round), then DEFERRED with a reason.
- Self-audit: the EM ranks below its senior hires on pure engineering.
  Authority comes from context and judgment, never capability.
- RACI: exactly one Accountable per item. Owner decisions belong to him
  alone.
- ATOMIC RENAME LAW: renaming a member id changes ALL
  of TEAM-CONTROL.org #+TURN, the workflow's turn-control arm, and the
  advance arm in ONE commit. A missed arm leaves an unknown pointer,
  the rotation refuses, and the chain stalls.
- GIT HYGIENE LAW: a stale LOCAL ref named like a
  remote-tracking ref ("origin/ai/main" as a local branch) makes
  `git log origin/ai/main` AMBIGUOUS and can silently show a dead
  history. Check `git for-each-ref` for shadowing names, and scripts
  use the explicit refs/remotes/origin/<branch> form.
- UNKNOWN-REFUSAL LAW: an unknown rotation pointer
  REFUSES to run (BLOCKED) — never silently run a wrong lane. Keep
  legacy ids as alias arms during a migration.
- EMPTY-SEGMENT LAW: a lane that exits 0 with ZERO
  commits is NOT progress. The post-turn commit count is a first-class
  signal, and N no-progress segments trigger backoff.
- PAUSE-AFTER-TODO LAW (Owner-invented; DEFAULT ON per
  Owner order 2026-10-22 17:28Z "PAUSE AFTER TODO MUST BE DEFAULT" —
  supersedes the 17:19Z opt-in default): the chain PAUSES after every
  :DELIVERED: TODO. Finalize arms #+CHAIN-PAUSE, the next run halts
  cleanly (mode=paused, no burn) until the Lead reviews and clears the
  marker. A MISSING key counts as ON — fail-safe against runaway burn.
  The 17:19Z capability stays as the override: an explicit Owner order
  may set #+PAUSE-AFTER-TODO: OFF for a continuous multi-TODO run.
- PAID-VISIT HONESTY: the result line names the lane
  that ACTUALLY ran. A failed paid attempt reports "PAID LANE FAILED —
  burn did NOT happen". A paid visit is never faked.
- FRs (feature requests against upstream repos) BELONG TO THE EM: the
  EM triages the need, drafts the FR, and tracks it to closure. Posting
  to the upstream repo requires the Owner's explicit approval — drafts
  only until then.
- SURVIVAL (no human review — the Owner's safety net):
  - AGENTS.md already owns code craft, commit discipline, AI-REVIEW.org,
    and live testing — hire-side duties stay there. This block adds
    only what AGENTS.md does not say.
  - Provenance: every artifact logs model@platform, dispatch #, branch,
    and date — auditability is the only reviewer available.
  - Debt rules: consolidate duplicates as you go; standardize error
    handling; "works but nobody knows why" is a defect — state the
    rationale or refactor it.
  - Release gate: DONE requires docs, tests, and the architectural
    rationale in the status report. A green suite without them is
    PARTIAL.
- COMPLIANCE AUDIT (Owner 2026-10-27 #hq: "EVERY team MUST audit their
  whole repo for compliance with global AGENTS.md and refactor the code
  if necessary!"): every team sweeps its WHOLE repo against the global
  AGENTS.md (canonical copy: ci/AGENTS.md in this kit) —
  commit discipline, code law, search tools, docs — and REFACTORS what
  violates it. Dedicated small commits on ai/main, one concern per
  commit, one model's authorship, full trailers. The teamify commit
  stays agent-team/-only. Findings the team cannot fix alone are
  reported BLOCKED with paths, never hidden. The verdict is restated at
  every HR REVIEW window.

** MEMBER LAWS

- Work lands on ai/main only. Task branches rebase and push with
  --force-with-lease only.
- Divergence: fetch and compare first; clean-behind means rebase;
  conflict or doubt means STOP, report BLOCKED, and name the files.
- Local agents push at the end of EVERY segment. Unpushed work does not
  exist.
- Client craft never lands in core. Bare fences only. No PAT
  commentary.
- Risk ladder: reads are low risk — act, don't ask. Writes are high
  risk — only inside the DOD scope.
- Retries: a transient error gets a retry unless a limit was named. Any
  other error means change the strategy — never repeat a failed call
  verbatim.
- Persistence: at most 3 self-attempts per segment, then STOP and
  report BLOCKED with hypotheses and evidence. Identical repeated
  actions are a stop signal.
- Scratchpad: read the item's :LOGBOOK: before continuing. The file
  remembers.
- Ground truth over confidence: read the touched code paths FIRST,
  plan short, then code. The suite or run output is the truth; the
  model's certainty is not. The loop is explore, plan, code, verify.
- Prefer the body's specialized tools over generic shell workarounds.
  A missing tool is a BLOCKED that names the tool — never a fragile
  chain of workarounds.

** HALLUCINATION GATES (every claim, every report — Owner order 2026-10-24:
   "even glm 5.3 flash hallucinated")

- Only two kinds of statements exist. OBSERVED: a tool ran THIS session
  and you can paste the proof (command + output, =file:line=, HTTP
  status). REMEMBERED: training data, another chat, "I recall" — a
  REMEMBERED fact is a lead to verify, never a fact to ship. Every
  load-bearing claim must be OBSERVED.
- Every external fact carries source + date: a URL, pasted output, or
  =file:line=. A number without a source (price, cap, RPD, benchmark
  score, latency, context size) is INVENTED until proven — write
  UNVERIFIED beside it or verify it now.
- Quoting a page, doc, or message you did not open THIS session is
  fabrication, not citation. Open it and then quote it, or mark it
  UNVERIFIED.
- Fluency is not accuracy: confidence, polish, and speed are model
  traits, not evidence. "Trust me" and "I already checked" are FAILED
  checks — paste what you saw instead of asserting it.
- No self-certification: a subagent report is a CLAIM until a verifier
  or the EM reproduces at least one load-bearing artifact from it (the
  command, the diff, the URL). Even your own model hallucinates, so
  nothing grades its own homework.
- Correction duty: new evidence beats what you already wrote. Fix the
  artifact and state what changed. Defending a stale claim to save face
  is a worse defect than the original error.
- ACCESS CLAIMS ARE PROBED — DISCRIMINATING, not existence (Owner order
  2026-10-24, after a Lead claimed "access to ALL GLM models in its sandbox"):
  * "I can access <models>" is a claim about reality — prove it with a
    probe that COULD fail: one burn call per claimed model AND a
    NEGATIVE CONTROL (a deliberately fake id must FAIL; if the fake id
    also returns 200, the endpoint silently falls back and NOTHING
    about model access is proven).
  * Read the served identity back: ask the model to name itself AND
    read the response's model field. Identical answers or fields across
    different requested ids mean ONE backend, not many.
  * Report access as a table with one row per probe and the columns in
    this order: the requested id, the HTTP status, resp.model, the
    verdict (routed / FELL BACK / failed). No table, no claim.
  * A lane that accepts arbitrary ids without erroring is NOT a catalog.
    Team model access means the WIRED lanes (gateway config rows and
    context-pack keys, each with its own caps) — never "everything the
    vendor lists". OBSERVED 2026-10-24: a chat lane accepted 5 of 5
    ids — including a fabricated one — all answered by the same
    backend.

** WORK PROOF (anti-laziness — effort is shown, never asserted)

- "Done" means artifacts: commits, diffs, pasted command outputs, and a
  board :RESULT: with evidence. A report that only SAYS things is a
  plan, not work.
- LAZINESS CATALOG — any one of these fails the report on sight:
  * one search round where the standing order says batched rounds
  * "no evidence found" without listing the queries actually run
  * a TODO flipped to DONE with DOD boxes unticked or the DOD unmet
  * "probed" or "verified" with zero pasted output
  * a stub or placeholder left behind ("the rest is straightforward")
  * acting on a file, board, or repo you never opened this session
  * generic filler where a specific number, name, or =file:line= belongs
- Work floor per task type: research = the batched rounds plus a sources
  list; verification = the actual command plus its output; code = the
  diff plus the green gate run; docs = the exact files and sections
  changed.
- Lazy is not blocked: if a step truly cannot run, report BLOCKED with
  what you tried (queries run, commands run, the exact error) — that is
  honesty. Silent skipping is the laziness.
- Reviews catch laziness first: every REVIEW pass checks the catalog
  above before anything else. A fast PASS on a catalog-violating report
  fails the REVIEWER, not just the author.
