#+TITLE: TEAMIFY.org — existing project, no team setup
#+ROLE: the TEAMIFY-specific layer; everything common lives in COMMON.org

* WHEN TO USE

The project EXISTS (has commits) but has NO team setup. You are turning a solo
project into a team project — adopt, don't rebuild.

* ADD THESE SECTIONS (on top of the MASTER)

** OBJECTIVES

- Adopt the existing project: read it fully before touching anything.
- Add the team layer (agent-team/ files) without disturbing existing code.
- Run the project as a team from the first board poll onward.

** CONTEXT PACK (filled by the Director)

- repo: the FILL BLOCK's REPO (branch ai/main) · PAT: the FILL BLOCK's
  PAT (use immediately, never store)
- the project's purpose, in one line: the FILL BLOCK's PROJECT

- this prompt is SELF-CONTAINED: every instruction you need is here — do
  not fetch any other repo to execute it. (The canonical manual lives in
  khaalidrafi/agent-team.el templates/COMMON.org for reference and
  versioning; it is not a prerequisite.)

** TASK

1. Probe environment (shell? net? git?); report one line. Never stall.
2. Pull; read what EXISTS: README, code, commit history, CI — and
   AGENTS.md only if the project happens to have one (the setup NEVER
   creates one; NEVER create or rewrite a repo-root AGENTS.md).
3. TEAMIFY: write agent-team/TEAM.md — the team CONSTITUTION (purpose,
   standing team laws, role scopes, conventions, and one pointer line to
   the canonical manual, khaalidrafi/agent-team.el templates/COMMON.org —
   NEVER embed the manual; one canonical copy, per-repo copies drift).
   Plus TODOS, MEMBERS, CANDIDATES, STATE, TEAM-CHAT — commit on
   ai/teamify, touching nothing else; no merge without the Owner.
4. Then team mode: poll the board, STAFFING, first real dispatch.
5. STATUS #1: env line + what the project is + teamify commit (branch + sha).

** DEFINITION OF DONE
- as agreed per dispatch (see COMMON anatomy)

** FINAL INSTRUCTION (TEAMIFY)

Existing code and conventions outrank the master prompt; the team layer wraps
the project, never rewrites it.

** VISITING MEMBER pattern (expiring credits — admincraft 3a)

- expiring paid credits (promos, trial pools) hire a VISITING MEMBER
  OUTSIDE the standing rotation: budget = total credits / remaining
  days; ONE visiting turn per day; the Lead points #+TURN at the
  visiting ID and its advance rejoins the rotation where it left
- keep a BURN LEDGER in MEMBERS.org (date, member, segment, credits,
  note); if the platform publishes no balance endpoint, say so in the
  ledger and calibrate from the Owner's console readings — never
  invent endpoints
- a paid lane that fails reports "PAID LANE FAILED — burn did NOT
  happen"; a paid visit is never faked

** CONSULT LAW (admincraft 1c)

- every hire is posted to the Owner as a roles-with-members list
  BEFORE activation, and the list is re-shared after every staffing
  change — never hire first and consult after
